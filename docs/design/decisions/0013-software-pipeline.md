# 0013 代码生成按软件流水剥掉稳态分支

## 状态

已接受（2026-09-27）。修订 ADR 0009 第 2 条和 ADR 0011 的守卫发射。对应评估协议 v2.8：M0 通过线的分母是去守卫、短 tile 的手写内核。

## 背景

ADR 0011 把循环按槽位展开，event id 变成字面量，但 WAR 仍可能留在 `if (gi >= stages)` / `if (gi + stages < TILES)` 里。短 tile 上这些标量分支会吃掉 M0 允许的执行时间差（生成中位不超过手写 5%，每一对不超过 10%）。协议把「去守卫的手写」定为通过线分母，所以生成结果也要去掉稳态里的 `if`。

## 决定

1. 按 WAR 签名把展开后的迭代分组。同一组里，每条 wait 要么始终发出，要么始终不发；notify 同理。
2. 单独一组写成直线代码，迭代号折成常量。连续多组收成一条 `for`，循环体里的 wait / notify 无条件发出。
3. vector add（`TILES = 8`，x/y `stages = 2`，z `stages = 1`，展开步长 2）因此是：prologue `i = 0`，稳态 `for (i = 2; i < 6; i += 2)`，epilogue `i = 6`。
4. event id 仍是字面量。同一 id 上 notify / wait 仍严格交替。agent 仍不写释放边。

## 后果

`examples/vector_add/add_golden.asc` 与 `add_reference.asc` 按同一份去守卫调度对齐。这一对的翻译差在指令流上应接近 0。上板计时仍要在 CANNBench 上做，本仓不代替那次测量。

## 推翻条件

- 某类合法流水无法切成「组内 WAR 决策恒定」的 prologue / 稳态 / epilogue，只能把 `if` 留在稳态里。届时该形状单独记一对，不把守卫写回默认发射。
- CANNBench 测出这份去守卫配对的中位差仍超过 5%，或任一对超过 10%。届时先查指令流是否真的对齐，再决定改发射，不把通过线改回带守卫的分母。
