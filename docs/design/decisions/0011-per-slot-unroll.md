# 0011 循环按槽位展开：event id 全字面量

状态：已确认（2026-09-26，复审第 1 条与核对项）。修订 ADR 0010 的发射方式。

## 背景

复审提出两点：

1. WAR 释放必须在槽位的**最后一次消费**之后，且每轮每个 buffer 只发一次。V003 放宽到「至少一个消费方」后，两条计算读同一槽位的核会在第一次读后就释放，并在同一 id 上连续 notify（UB）。
2. 核对项：WAR 的 event 是运行时三元表达式 `((i % 2) == 0 ? EVENT_ID0 : …)`；若 `asc_sync_notify`/`asc_sync_wait` 的 id 要求编译期立即数，这行编不过。

## 决定

1. **循环按流水深度展开**：`for (i = 0; i < TILES; i += N)`（N 为各 buffer stages 的最小公倍数），每个槽位一段代码，event id、槽位偏移、WAR 守卫全部是编译期字面量。TILES 不能被整除时拒绝生成。
2. **WAR 释放点**：循环体内该槽位最后一次消费的语句之后；同一语句重复读同一 buffer 只释放一次。发射端预计算每 buffer 的「最后读语句下标」。
3. 守卫按全局迭代号 gi = i + k 推导并化简：等待 `gi >= N`，释放 `gi + N < TILES`；恒真/恒假时分别省略守卫或整行。

## 后果

- 生成代码不再出现运行时三元/取模；顺带回应了「守卫分支开销」的评审关注（守卫数量不变，但取模和指针运算消除）。
- 新约束：TILES % lcm(stages) == 0，违反时 CodegenError 并给出调整建议。
- v0.2 不支持跨 PIPE 就地改写（一个 buffer 的生产 PIPE 必须唯一）；直写形态的就地 RMW 由发射端以此理由拒绝，spec 已写明。

## 推翻条件

- 头文件核对证明 event id 可以是运行时值（三元可回退，但展开仍更优）。
- 真实内核需要 TILES 与流水深度不互整——届时加尾轮（epilogue）发射而不是放宽整除。
