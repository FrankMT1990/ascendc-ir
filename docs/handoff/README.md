## 现在不要做的事

- 不要开始正式的 C1（每臂 5 次）。预算 B 还没定，任务也还没分类。
- 不要为了分类再测一遍向量加。现有的 2.006 μs 是 32 核 aclnnAdd，4.370 μs 是单核拷贝下界，不是同一口径。
- 不要用开发套件头文件覆盖这台机器上的 CANN 9.1.0。
- 不要改核里的计算去凑编译。缺符号就记下符号和编译器原文。
- 不要把 `evals/c1/freeze.json` 里的草稿当成已经封存的协议。它还没进 Git，W2 的理由也过时了。
- 不要提交工作区里那些与本次任务无关的改动（大量 ADR、`evals/m4_m5`、`examples/vector_add` 的换行差异）。

## 接着做的顺序

1. 对照 cann-bench level1，列出「当前代码生成真能发出的指令」与 level1 的全部交集。空集就记未测，不要为了有任务而加一个向量加。
2. 给清单里的每个任务准备同一口径的 `T_baseline` 和 `T_HW`：同一台 Ascend950PR_9589、CANN 9.1.0、CANNBench kernel-only、和计时输入同一 shape。两项缺一，该任务保持未分类。
3. 把容差、golden、计时输入的哈希，以及逃逸扫描和对照臂越面扫描，在第一份试点发出之前写进仓库。
4. 按 `docs/evaluation/claims.md` 核对检查器五类注入。任一类没有封存注入，C3 就是未测，停止，不要进 Agent 环。
5. 只有 1–4 都进仓之后，才按 `evals/c1/freeze.json` 草稿里的试点顺序做试点，用来定 B。试点不计入正式 5 次。
6. B 写回冻结文件之后，才发正式包。W2 没有按协议测过时，整项 C1 最多记「部分成立（W1）」。

每完成一步，把结果写进当天记录并推到 GitHub。正式对比的结果推独立分支，不要改写已经封存的哈希。
