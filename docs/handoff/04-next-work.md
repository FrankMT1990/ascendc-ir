# 下一步

性能对比是 C1，不是再编一遍 `pack/board_3510`。下面按必须完成的顺序写。前面一步没进仓库，就停，不要跳到试点或正式 5 次。

## 1. 写出任务清单

打开 cann-bench 的 level1 任务列表。对每一项问：当前 `master`（`3acb588`）的代码生成能不能发出完成该任务所需的全部指令。

交集里的每一项都留下，包括你预期会带宽顶满的项。交集为空就在记录里写「未测」，不要把向量加单独塞进去凑数。

向量加可以留在清单里，但它不能用来证明时间增益。它已经贴着单核拷贝下界。

Cube 任务只有在代码生成真能发出时才进入清单。f16、K 可分块、B 按 `(n, k)` 存放、结果为 A @ B.T 的矩阵乘可以进入。f32 转置矩阵乘、`mmad_mx`、mix 启动不能进入。

改写 `evals/c1/freeze.json` 时删掉「v0.2 没有 Cube 词汇」。W2 改成：清单里有 Cube 任务则为待测，否则写明未测的原因是 level1 里没有可生成的 Cube 任务。

## 2. 封存每个任务的两个时间

对清单中的每个任务，在 Ascend950PR_9589、CANN 9.1.0 上，用 CANNBench kernel-only 测：

- `T_baseline`：该任务重测基线，shape 与将来的计时输入相同。
- `T_HW`：同一 shape、同一计时入口下的硬件时延下界。

两项写入冻结文件，并记下输入哈希。缺任何一项，该任务 `kind` 保持 `unclassified`。收包之后不准补 `T_HW` 把未分类改成带宽顶满。

空隙 `h = T_baseline / T_HW − 1`。`h ≥ 0.20` 标调度敏感，否则标带宽顶满。不要用 2.006 μs 或 4.370 μs 或 M0 的 4.398 μs 填这两个字段。

这一步是性能验证之前的第一次上板。它不是 Agent 对比。

## 3. 封存数值门和扫描

在第一份试点发出之前，把下面内容提交到仓库，并记下哈希：

- 容差文件：比较式只允许 `abs(输出 − golden) ≤ atol + rtol × abs(golden)`，在 golden 的 dtype 上比较。
- 每一组必测输入和对应 golden。
- 每个任务唯一的计时输入组，且与 `T_baseline` 同 shape。
- IR 臂逃逸扫描、对照臂越面扫描，以及它们的反例。

`examples/`、参考 `.asc`、asc-devkit 示例内核对两臂都不可见。

## 4. 确认 C3 不是未测

按 `docs/evaluation/claims.md`：UB、对齐、event 配对、跨 PIPE、未初始化，每一类都要有封存注入，召回各自 ≥ 0.9，误拒为 0，定位命中 ≥ 0.8。任一类没有封存注入，就停。不要用总召回代替某一类。

现有 `evals/m4_m5` 工作区是脏的，先看已提交的版本，不要把未提交的换行差异当成新注入集。

## 5. 试点定 B

1–4 都进仓之后，按提交时间做试点。取前两次成功试点的首次正确 `completion_tokens`，最大值乘 3，得到 B。不足两次就继续，追加最多 4 次，全部归档，不得挑选。仍不足则 B 未定，正式 C1 不开跑。

试点 id 与正式 run 的 id 在第一份正式包发出前写入仓库。试点不计入 R=5。试点期间不得改任务书、容差和扫描脚本。每 run 上板不超过 20 次。

## 6. 正式对比

B 写回冻结文件之后才发正式包。每臂 5 次。判词只查 `claims.md` 的表。

- 调度敏感且 `rel ≥ +0.20`，才算时间上的增益成立。
- 带宽顶满的任务，成功次数够就可以成立，不要把「没有变快」写成失败。
- W2 未测时，整项最多是「部分成立（W1）」。
- 噪声底没有封存时，不要用 −0.05 判输。

结果写独立分支，附上收包时的 csv 哈希。不要改写已经封存的哈希，也不要把后到的包拿来递补缺档。
